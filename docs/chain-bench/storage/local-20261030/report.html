理论与实测能否对应？

能对应。账户记录大小、公钥槽数和 Storage Trie 节点数均与当前合约结构吻合。下面以百万账户阶段核对；实测为三个节点分别扣除基线后的平均值。理论只计新增账户本身，实测仍包含测试期间其他状态的增长。

1. 单个账户增加了什么？

EOA 和合约账户都有 nonce、balance、storageRoot、codeHash，不是 PQ 账户才新增后两个字段。EOA 的根与代码哈希指向空内容；本实验的 ML、SLH storage 账户都有非空 storage 和代码。

2. 理论大小怎样计算？

账户 snapshot：EOA 为 38 bytes，两个 PQ 方案均为 103 bytes。数据库键是 1 byte 前缀＋32 bytes 账户哈希，共 33 bytes。精简 RLP 会省略空根和空代码哈希：本实验 EOA 的值占 5 bytes，合约账户的值占 70 bytes，因此分别为 33＋5＝38、33＋70＝103 bytes。差额 65 bytes 包含 RLP 长度前缀变化，不是简单多存两个 32 bytes 字段。

Storage snapshot：SLH 约 98 bytes，ML 约 4,086 bytes。每条记录的键是 1＋32＋32＝65 bytes；完整 32 bytes 槽值经 RLP 编码通常为 33 bytes。SLH 为 65＋33＝98 bytes；ML 的 41 个数据槽为 41×98＝4,018 bytes，长度槽保存 1,312×2＋1＝2,625，编码占 3 bytes，该记录为 65＋3＝68 bytes，合计 4,086 bytes。槽值前导零可能使编码略短。

Storage Trie：SLH 约 103 bytes，ML 约 7,084 bytes。SLH 单槽只需一个根叶节点：33 bytes 数据库键＋通常 70 bytes 节点编码。ML 的 42 个槽位经哈希后，按当前 MPT 路径构成 59 个持久化节点；计入路径键和节点 RLP 后约为 7,084 bytes。这是当前槽位布局与通常编码长度下的结果，不是任意 42 个槽的通用常数。

同一账户数、同一口径：总增量倍数＝平均单账户增量倍数。每节点平均值为三节点增量之和÷3；再除以账户数才是每账户平均值。实测 ECDSA 分母包含少量背景 storage，因此实测倍数略低于只计算账户本身的理论倍数。

账户 Trie 也符合预期：三个方案的百万账户增量均约 156 MiB。主 Trie 中的账户值保留固定长度的根和代码哈希；账户数量相同、地址分布近似随机，因此规模接近，PQ 新增存储主要体现在各账户的 Storage Trie。

5. 为什么实际磁盘倍数不同？

理论校验针对数据库逻辑内容；实际磁盘还受压缩、数据库组织、交易历史、索引和后台整理影响。前面的“落盘 bytes/账户”是全链磁盘增长的平均分摊，不是账户结构的固定大小。逻辑大小不能直接相加后当成磁盘占用，也不能由 42／1 个槽直接推导磁盘放大倍数。
