Bench 优化与本地验收

通过并发流水线、账户缓存和原生 SLH 签名，提高有效发送能力；同时修复大签名打包超限。三种账户的创建、转账、停止与回执恢复均通过本地验收。

2026-11-02，Apple M1 Pro / macOS arm64、Node.js v25.9.0。本地 3 个 Validator、1 个 Bundler、1 个 Bench；这是功能与容量诊断，不是远程三机的饱和吞吐结论。

改了什么

  • 线程与在途数分开。--workers 控制计算线程，--max-inflight 控制构造、签名、发送及等待回执中的操作数；同一账户仍只允许一笔在途操作。
  • 复用账户对象。账户固定分给 worker，LRU 缓存有上限；不缓存 nonce 或签名。准备和创建阶段每账户只处理一次。
  • SLH 可选原生后端。--slh-backend openssl 使用常驻进程与 CPU 的 SHA 实现；原密钥、Pure 模式、空上下文和链上预编译不变，默认仍为 noble。
  • 定位各阶段开销。记录签名、RPC 提交、回执等待及限速等待的次数、均值与最大耗时；按时停派、持久化日志和未决请求保护保留。

高并发暴露的两个打包问题

  • 交易编码超限：16 笔 SLH 操作合并后约 136 KB，超过 BSC 的 128 KiB 限制。所有本地 PQ 路线现在按实际 calldata 长度拆包，并预留 1 KiB 外层编码空间。
  • gas 下限重复计算：Alto 将整批 calldata 的 gas 按操作数反复累加，造成约 3,250 万 gas 的请求被节点拒绝。现改为整批只计一次，保留实际 gas 估算与 AA95 保护。

新增测试覆盖分包不丢单、不重复，以及 EntryPoint v0.6 / v0.7 的 calldata gas 计数。失败测试记录保留在私有 runtime；本地未决操作用原签名恢复后逐笔核对，未把失败轮次计入成功容量结果。

如何继续压到瓶颈

  1. ECDSA / ML 先增加在途上限，再看提交率是否提高；不用把 worker 堆到几百。SLH 先启用原生签名，再按 CPU 余量增加 worker。
  2. 缓存覆盖该 worker 反复使用的账户。例如三客户端共享 1 万账户、每客户端 16 worker，每 worker 缓存 256 个账户即可覆盖分片。
  3. 只有发送率达到目标，链侧 gas、txpool、出块及最终化指标才有助于判断饱和。签名、Bundler 模拟或回执等待受限，应先定位对应组件。
  4. 多角色同机争抢 CPU；需要更高压力时，可通过现有配置把 Bench、Bundler 与 Validator 分机。逐档提高 QPS，保留监控及异常停压。

阶段耗时是已结束调用的墙钟统计，并发可重叠，不能相加当作 CPU 时间。ECDSA 已在启动时核对链身份，签名前校验 chainId 后直接本地签名，省去逐笔重复的链 ID RPC。Linux x86_64 构建与远程性能仍需在目标机器验收；不直接套用本机吞吐。

验证与复现

通过 18 项 Bench 单测、120 项远程管理测试、19 项 one-box 回归，以及真实链上的密钥、公钥、余额、并发 nonce、重复 run、缓存、到时停派和停止恢复检查。

node tools/chain-bench/load/signer/capacity.mjs

中控更新后先 build，再 upgrade，保留原账户池与链数据。新参数不填写时沿用原并发规模和签名后端。
