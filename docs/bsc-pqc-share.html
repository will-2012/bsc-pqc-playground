1. 背景：量子风险与迁移需求

量子计算的发展对 BSC 的长期安全提出了挑战。未来，足够强的量子计算机可利用 Shor 算法破解账户签名和共识投票所依赖的椭圆曲线密码学，威胁资金与共识安全。目前尚无量子计算机能在实际条件下完成这类攻击。

密码学迁移需要时间。BSC 应参考业界进展，提前验证抗量子方案及其成本，优先探索金库等高价值资产的保护方式，为分阶段迁移做好准备。

本次探索：通过 ERC-4337 智能合约金库，接入 ML-DSA-44 与 SLH-DSA-SHA2-128s，验证高价值账户的抗量子方案及其成本。

参考：BNB Chain 抗量子迁移报告 · BEP-707：BNB Chain 整体迁移路线 · BEP-713：BSC 迁移路线。

2. 业界进展、技术取舍及对 BSC 的启发

2.1 ETH

2.1.1 风险模型

ETH 密码学基础 = 椭圆曲线密码学＋哈希函数

2.1.2 PQC roadmap

核心性能挑战：计算成本＋数据成本。

维度主要开销对 ETH 的影响
计算成本 签名、验签、证明生成、递归聚合与证明验证；还需关注内存需求。 能否在出块时限内完成，以及节点参与所需的硬件门槛。
数据成本 公钥、签名、证明及必要元数据的传输、缓存与持久化。 网络带宽、传播延迟、磁盘占用与同步成本。

应对思路：用聚合缓解数据膨胀，将新增计算分层承担。更大的签名带来突出的传播与存储压力。ETH 的研究路线是将大量交易签名、验证者投票的有效性汇总为证明，减少原始签名的重复传播与全网验签，但会增加证明生成的计算。

为减轻出块时的计算压力，交易在内存池传播阶段提前聚合，投票由具备算力的聚合节点分层处理，再由构块者或提议者完成最终汇总。聚合在链下进行，但仍须满足出块时限。

具体草案
  1. 账户层：账户抽象＋签名与证明聚合。
    EIP-8141：原生账户抽象；EIP-8288：交易签名与证明的递归聚合。
  2. 共识层：哈希签名＋投票证明聚合，配套密钥管理与随机数改造。
    EIP-8450：验证者 PQ 公钥登记；EIP-8292：投票证明聚合角色；EIP-8310：有状态签名密钥管理；EIP-8321：哈希链 RANDAO。具体签名与共识规则见 leanSpec。
  3. 数据层：抗量子承诺＋数据可用性抽样。
    LeanDA 研究：用纠删码、哈希承诺与编码正确性证明，探索替代 KZG 的抗量子方案。
  4. 网络层：抗量子认证＋密钥协商，不强求全部使用哈希方案。
    抗量子 RLPx 握手研究：探索基于 KEM 的执行层节点认证与密钥协商。

2.1.3 对 BSC 的启发

ETH 的优势：覆盖全面，核心一致，账户灵活。各层协同迁移，尽量共享密码学与证明基础设施，同时保留账户的算法选择能力，整体设计较为统一。

代价：系统复杂，迁移周期较长，关键环节仍需验证。原生账户抽象的协议集成、递归证明的性能，以及聚合节点的算力供给与激励，都影响落地进度。将计算交给聚合节点，可以减轻普通节点负担，但也引入可用性与集中化问题。

对 BSC 的启发：长期跟进，短期聚焦。

  1. 长期尽量跟进 ETH 路线。复用成熟方案，保持兼容，并结合 BSC 的出块时限与节点条件，分层、逐步迁移。
  2. 短期先探索高价值账户的量子安全保护。借鉴账户抽象思路，通过 ERC-4337 智能合约金库接入抗量子签名，无需等待全链改造完成，再用实验验证安全性与成本。

2.2 TRON

思路：直接扩展协议签名能力，优先控制数据与验签成本。TIP-899 覆盖交易、出块、节点中继握手及合约验签，先建立基础抗量子能力，不以证明聚合为前提。

具体方案
  1. 协议改造：在现有 Transaction、BlockHeader、HelloMessage 中增加 PQAuthSig，携带算法标识、公钥与签名；按算法分派验签，并补充 TVM 预编译。这里扩展的是签名字段，并非新增交易类型。
  2. 账户迁移：复用现有 Permission，通过权限更新配置抗量子密钥对应的地址与权重，保留原账户地址和资产。Account／Permission 结构不变；第一阶段每笔交易携带完整公钥。
  3. 算法选择：支持 Falcon-512 和 ML-DSA-44，分别控制启用。Nile 已有 Falcon 启用测试记录；Falcon 体积小、验签快，但对应的 FN-DSA 标准尚未定稿。ML-DSA-44 已标准化，作为备选，代价是公钥与签名更大。

取舍：路径直接，优先性能与落地。这一阶段无需等待 ETH 的账户抽象与证明聚合路线成熟，但仍需承担大签名的传播与存储成本。两种算法均属格密码，尚未提供哈希签名这一不同安全假设的选择；这不意味着格密码已被量子算法攻破。

对 BSC 的启发：ML-DSA-44 可作为金库的候选算法，在标准化、计算成本与签名大小之间取得平衡，并与哈希签名方案对照验证。

参考：TIP-899 及 Nile 测试讨论 · NIST 标准化状态。

2.3 SUI

思路：原生账户兼顾性能与安全余量，合约金库提供不同安全假设的选择。Sui 选择两种已标准化的算法，分别用于原生账户认证和 Move 金库。

具体方案
  1. 原生账户：ML-DSA-65。采用格密码，遵循 FIPS 204；选择 NIST 安全类别 3，较 ML-DSA-44 留出更多安全余量，同时保持较低的验签开销。这里改造的是账户认证，不代表共识签名也已替换。
  2. 高价值金库：SLH-DSA-SHA2-128s。采用基于哈希的 FIPS 205 算法，通过 Move 合约控制资产操作。安全假设较保守，且合约方案便于适配后续算法；代价是签名更大、验签更贵。
  3. 进展：Devnet v1.82.0 已加入 ML-DSA-65 相关接口与验签支持；金库是单独的合约路线，不能由原生账户的 Devnet 进展推断其主网上线状态。

取舍：标准化、算法多样性与安全余量并重。格密码与哈希密码提供不同的安全假设，用户可按用途选择；这不意味着哈希方案在所有方面都更安全，也不是每个账户必须同时使用两种签名。

对 BSC 的启发：借鉴“标准算法＋不同安全假设＋合约金库”的组合，先通过 ERC-4337 金库探索高价值账户的量子安全保护。ML-DSA-44 与 SLH-DSA-SHA2-128s 可作为两条实验路线，对照安全类别、签名大小和交易成本。

参考：Sui 官方选型与权衡 · Devnet 发布记录。

3. BSC 抗量子方案思路

3.1 选型及权衡

长期跟进 ETH，短期先做抗量子金库。长期尽量复用 ETH 的成熟技术，分层推进协议迁移；短期借鉴账户抽象与合约金库模式，优先探索高价值资产的量子安全保护。

短期方案：ERC-4337＋两种可选的标准签名。通过用户态账户抽象，由智能合约钱包验证抗量子签名，Bundler 负责提交交易。高价值账户可将资产迁入金库，按需选择 ML-DSA-44 或 SLH-DSA-SHA2-128s。

价值：先保护重点资产，保留后续演进空间。无需等待原生账户抽象与全链迁移完成，即可验证金库方案；账户可自定义验签的方向与 ETH 长期路线一致，未来协议与接口仍需适配。成本则通过后续算法基准和链路实验量化。

依据：ERC-4337。算法与交易成本见第 3.2、4 节。

3.3 ERC-4337 抗量子方案

将资产放入智能合约账户，由抗量子签名决定能否动用。钱包生成密钥、签署操作；Bundler 将操作打包为普通交易；链上的 EntryPoint 与账户合约完成验证和执行。

3.3.1 整体架构

3.3.2 创建 PQ 智能账户

共享的 EntryPoint、Factory 和验证器先行部署。用户随后生成自己的密钥，预测账户地址，并通过首笔 UserOperation 完成账户创建。

创建由 EntryPoint 经 SenderCreator 调用 Factory 完成，账户地址由工厂、部署代码、公钥与 salt 等共同确定。本地创建命令的首笔操作为零金额自调用，用来验证“部署＋授权”链路；已有账户后续不再携带部署参数。

3.3.3 发送 PQ 操作

模拟不是最终授权。区块执行时仍由 EntryPoint 调用账户验签，验证通过后才能执行；验签通过也不代表业务调用一定成功，需要检查 UserOperation 的执行结果。

费用：本地未使用 Paymaster。Bundler 先垫付外层交易 gas，EntryPoint 再从账户的预付资金中结算。

实现依据：本地钱包流程 · PQAccount · Factory · ML-DSA-44 账户 · ERC-4337。
