本报告为 BSC 的 ERC-4337 抗量子账户选型提供参考，比较签名大小与本机计算成本。六项算法共用 Go 接口，每次签名 / 验签调用一次 C 后端，计入 Go 和 CGO 开销；不含密钥生成和可复用对象创建。完整交易 gas 见链路报告。

权衡与启发

本项目可优先探索“ERC-4337 智能账户承载 PQ 金库”的路径，重点比较 ML-DSA-44 与 SLH-DSA-SHA2-128s。前者侧重较低的计算和数据成本，后者提供基于哈希的安全假设。算法选择之外，还要结合完整交易费用、授权设计和钱包使用成本判断。

  1. TRON：侧重紧凑签名与验签效率。TIP-899因 Falcon-512 的数据体积较小而优先选择它，同时实现 ML-DSA-44 作为已标准化的备选；Nile 已先启用 Falcon 路径。本轮 Falcon 的验签表现也较好，但这不是 TRON 客户端的性能实测。其取舍是接受较复杂的签名采样实现，以及对应 FN-DSA 标准尚未定稿带来的适配和审计风险。Falcon 已被 NIST 选中，不能简单称为“未经标准化评审的算法”。两种备选都属于格密码，尚未提供格与哈希两类安全假设的选择。
  2. Sui：留安全余量，按用途选择算法。官方方案为原生账户选择类别 3 的 ML-DSA-65，接受更大的公钥和签名，为密码分析进展留余量；为高价值金库选择在 Move 合约中验证 SLH-DSA-SHA2-128s。日常交易与资产保管因此可以采用不同方案。这里的“更保守”是指哈希安全假设，并非金库的 NIST 类别更高：128s 为类别 1，ML-DSA-65 为类别 3。两类算法可选，也不等于同一账户受到双重保护。
  3. 对 BSC 的启发：先提供可选金库，再逐步扩大覆盖。ERC-4337 允许智能账户自定义授权，资金可以由 PQ 签名控制，不要求所有用户同时更换账户。它是承载金库的框架，不是现成的金库产品；支出策略、密钥保管和恢复机制仍需另行设计。这是本项目的研究建议，不是 BSC 官方路线。ERC-4337 规范

ML-DSA-65 可作为更高安全类别的选择；Falcon 保留为紧凑签名对照；128f 则主要用于观察签名延迟的取舍。本轮 128f 比 128s 签名约快 20.8 倍，但签名约大 2.18 倍、验签耗时约为 2.84 倍，对低频金库的优势有限。

为什么同时保留格与哈希？格密码已有数十年研究，不能简单称为研究时间短或不安全；但具体构造和实现仍需持续审视，经典与量子密码分析也在发展。部分格签名的分析进展不代表攻击适用于 ML-DSA 或 Falcon。哈希签名可追溯至 20 世纪 70 年代，主要依赖哈希函数的安全性质，通常被视为更保守的路线，但具体构造和实现仍需审查。提供两种选项，是保留不同安全假设下的选择，不是否定格签名。若要求两类签名共同保护同一金库，需要两者同时通过；允许任一签名授权不具备这种保护。研究背景

优先保护高价值资产，是迁移顺序，不是小额账户的安全保证。可以先保护储备资金、项目金库和重要管理权限，再逐步覆盖日常账户。量子攻击若成本较高，攻击者通常更有动力选择预期收益高的目标；但未来成本尚不确定，小额账户也可能控制大额资产的授权，不能只按账户余额判断风险。

本地验证到哪里，方案就说明到哪里。当前已验证 PQ 签名、Bundler、EntryPoint 和智能账户的创建与转账链路；账户固定公钥和验证器，没有升级、恢复或换钥入口，也尚未实现完整金库产品。v2 / v4 依赖修改后的 BSC 客户端提供实验预编译，不能直接部署到未支持这些预编译的网络；v1 的 Solidity 验签无需新增 PQ 预编译，但成本较高。本地 Bundler 使用实验预算，联通成功不代表兼容公共 Bundler，详见链路报告和钱包说明。

生产金库还需覆盖所有资产转出与权限变更路径：传统签名不能通过升级、恢复、管理员权限或已有代币授权绕过 PQ 校验。ERC-4337 本身不提供抗量子保证，账户授权改造也不解决 BSC 共识、P2P 和 Bundler 外层交易的量子风险。

测试说明与参考

结果用于本机实现对比。耗时排名不代表安全等级，不能直接换算交易 gas，也不能与链路报告的 CPU 数据直接横比。

安全标注。“抗量子”指在相应参数与安全假设下抵抗目前已知的量子攻击，不是无条件安全。NIST 类别 1–5 不是直接标注的 bit 安全强度，ECDSA 不适用；标准发布也不代表本实验实现通过 FIPS 认证。128s / 128f 同属类别 1，ML-DSA-44 / 65 分属类别 2 / 3。

大小口径。“存储”指编码大小，不是对象内存或链上存储 gas。ML 私钥为展开编码，不应与 32 bytes 种子备份直接比较；SLH 的 64 bytes 私钥含 32 bytes 公钥；ECDSA 的 64 bytes 签名不含恢复位。Falcon 公钥 / 私钥省略固定的 1-byte 头，完整编码为 897 / 1,281 bytes；签名保留头部。617–667 bytes 是本适配器接受范围，本轮实测 648–661 bytes，并非通用长度上限或 TVM 的固定 666-byte 槽。

测试方法与验证
  • 执行与计时：同一 Go 程序单线程顺序运行，设置 GOMAXPROCS(1) 和 LockOSThread；循环预分配缓冲区、关闭 Go GC。每次调用一次 C 后端，不在 C 内批量摊薄 CGO。主指标由同一 CGO 时钟接口读取线程 CPU，另存墙钟和进程 CPU。Go 后台线程不计入主线程 CPU；进程 CPU 仅作辅助。
  • 数据与轮次：共用 4,096 条、每条 32 bytes 的公开语料及相同索引。每项 5 轮 × 7 批，每批签名 32 次、验签 256 次；每轮换钥并轮转算法顺序。共签名 1,120 次、覆盖 1,120 条消息；验签 8,960 次，每轮复用最后 32 对消息和签名，覆盖 160 条消息。
  • 签名输入：ECDSA 将这 32 bytes 作为摘要，其余作为原始消息；ML / SLH 使用 Pure 模式和空上下文，内部哈希计时。随机数、拒绝采样、编码及验签均保留。ECDSA 使用确定性 nonce，ML / Falcon 读取系统新熵，SLH 使用 OpenSSL 安全 DRBG；随机数开销并不相同。
  • 初始化边界：密钥生成、可复用对象创建不计时。ECDSA 复用公钥对象，ML 复用展开密钥；SLH 每次 EVP reset / Init 计时；Falcon 每次签名重新解码密钥，不缓存展开的 FFT 密钥。主表不包含各算法全部初始化成本。
  • 后端与编译：ECDSA 用 libsecp256k1，ML 两参数用 mldsa-native，Falcon 用原版 Falcon NEON，SLH 用 OpenSSL C / ARM SHA-256。共同 C 参数为 -O3 -mcpu=apple-m1 -DNDEBUG -fno-fast-math -ffp-contract=off，保留 ARM 汇编 / NEON；统一接口和编译参数不代表底层优化程度相同。
  • 正确性检查：每轮 32 个正例，以及消息篡改、签名篡改、截短和错钥四类负例。计时调用均检查成功，每批签名结束后重新验签；ML 与 OpenSSL 互验，Falcon 通过公开 KAT 和 NEON 上游测试。原始数据复算检查索引、次数、尺寸、顺序及 ECDSA 倍数。

macOS 不保证固定性能核或频率；环境、电源和温度快照保存在原始记录中，少量波动不能解释为普适优势。
