签名算法对比 · Go 接口

Apple M1 Pro · macos-arm64 · 2026-10-27

六项算法共用 Go 接口，每次 Sign / Verify 调用一次 C 后端，计入 Go 和 CGO 开销。密钥生成和可复用对象创建不计时，ECDSA 复用已解析的公钥对象。这是本机热密钥测试，完整交易 gas 见链路报告。

测试口径

  • 同一 Go 可执行文件、单线程顺序测试；GOMAXPROCS(1)、LockOSThread，计时循环预分配缓冲区并关闭 Go GC。没有在 C 内部批量操作以摊薄 CGO。
  • 使用同一 4,096 条、每条 32 bytes 的公开语料池。每项 5 轮 × 7 批，每批签名 32 次、验签 256 次；每轮换钥并轮转算法顺序。本轮签名实际覆盖 1,120 条消息；验签每轮循环最后 32 对消息和签名，共覆盖 160 条消息。各算法使用相同索引。
  • ECDSA 签署 32 bytes 摘要；其余签同一 32 bytes 原始消息。ML / SLH 是 Pure、空上下文，内部哈希计入。安全随机数、拒绝采样、签名编码与验签均不省略。ECDSA 是确定性 nonce，ML / Falcon 读取系统新熵，SLH 使用 OpenSSL 安全 DRBG；随机数需求与实现不同，不宣称等量随机计算。
  • 密钥生成和可复用对象创建不计时；SLH 每次调用的 EVP reset / Init 仍计时。ECDSA 公钥对象和 ML 展开密钥可复用。Falcon 每次动态签名都重新解码密钥，不缓存展开的 FFT 密钥。不同算法的初始化成本并未全部放入主表。
  • 共同 C 编译参数：-O3 -mcpu=apple-m1 -DNDEBUG -fno-fast-math -ffp-contract=off。各库保留适合 ARM 的汇编 / NEON，编译选项相同不代表内部优化程度完全相同。
  • ECDSA 用 libsecp256k1；ML 两参数用同一 mldsa-native；Falcon 用原版 Falcon NEON；SLH 用 OpenSSL C / ARM SHA-256。外层接口相同，底层实现与优化程度不同。

线程 CPU 由相同 CGO 时钟接口读取，锁定同一 OS 线程；另存墙钟及进程 CPU。macOS 不保证固定性能核和频率，环境、电源与温度快照保存在原始数据中。

验证与判断

每轮 32 个正例及消息篡改、签名篡改、截短、错钥四类负例；所有计时调用检查成功，签名每批末重新验签。ML 两参数与 OpenSSL 互验；Falcon 通过公开 Falcon KAT 及 NEON 上游测试。每项正式签名 1,120 次、验签 8,960 次。原始数据复算同时检查语料索引、次数、尺寸、顺序和 ECDSA 倍数。

本轮 128f 比 128s 签名快，但签名更大、验签更慢；两者均为 NIST 类别 1。ML-DSA-44 / 65 分属类别 2 / 3，较大参数带来更多计算和数据。Falcon 签名小、验签快，但签名采样实现较复杂。耗时排名不等于安全等级，也不能直接换算交易 gas。

算法定义、采用场景与来源

ML / SLH 分别依据 FIPS 204 / FIPS 205；本表采用原版 Falcon-512；NIST 页面在本次核查时仍将其对应 FIPS 列为待发布，不能等同 FN-DSA 定稿实现。采用场景依据下列提案与固定提交：TIP-899 仍是草案，不表示 TRON 主网已启用；所引 Sui 提交仅对 Devnet 启用 ML65，Move 金库选型不证明主网部署或使用量。
